# ADR-0001: Arquitectura de la CLI «tareas con IA»

- **Estado:** Aceptado
- **Fecha:** 2026-11-17
- **Contexto del proyecto:** Proyecto 2 de DAM (2º DAM), CLI para gestionar
  tareas asistidas por IA, con fines educativos.
- **Repositorio:** `cli-tareas`, rama `main`, commit base `c67291c`.

## 1. Problema que resuelve el proyecto

El proyecto necesita una herramienta de línea de comandos que automatice
tareas repetitivas del sistema de ficheros (listar, contar, buscar, resumir,
describir y clasificar carpetas) de forma segura, configurable y verificable,
incorporando además capacidades de IA en las dos últimas acciones.

Sin esta herramienta, cada operación requiere comandos manuales propensos a
error, sin control de qué acciones están permitidas, sin datos de entrada
centralizados y sin forma de prever el efecto de una operación antes de
ejecutarla.

Requisitos clave derivados del problema:

1. Interfaz de terminal coherente, con ayuda y tipado de argumentos.
2. Acciones configurables sin tocar el código fuente.
3. Seguridad: previsualizar efectos (`--simular`), validar configuración y
   limitar resultados.
4. Calidad comprobable mediante pruebas automatizadas (189 superadas).

## 2. Decisiones de stack: Python 3.12, uv, Typer y Rich

### Python 3.12

- **Justificación:** versión estable del ciclo de soporte, obligatoria en el
  enunciado del proyecto; permite sintaxis moderna usada en el código
  (tipado con `Path | None`, `dict[str, type]`, genéricos nativos) sin
  dependencias de retrocompatibilidad.
- **Alternativas descartadas:** Python 3.10/3.11 (menor soporte y sintaxis
  más limitada), versiones EOL (sin parches de seguridad).

### uv

- **Justificación:** gestiona entorno virtual, dependencias y ejecución de
  scripts con un solo fichero declarativo (`pyproject.toml` + `uv.lock`).
  Los comandos del proyecto (`uv sync`, `uv add`, `uv run tareas`,
  `uv run pytest`, `uv run ruff check .`) son uniformes y reproducibles.
- **Alternativas descartadas:** `pip` + `requirements.txt` (no gestiona
  venv ni resuelve dependencias con lock), `poetry` (más pesado, flujo
  paralelo al nuevo estándar PEP 621 ya usado en el proyecto), `pipx`
  (orientado a instalar apps, no a desarrollar).

### Typer

- **Justificación:** define la CLI con funciones tipadas y docstrings que se
  convierten automáticamente en `--help` (verificado: `tareas --help`).
  Soporta argumentos (`Path | None`), opciones (`--simular`, `--termino`,
  `--extension`) y agrupación de comandos. El punto de entrada es
  `[project.scripts] tareas = "cli_tareas.main:app"` en `pyproject.toml`.
- **Alternativas descartadas:** `argparse` (verboso, sin tipado, ayuda
  manual), `click` (predecesor de Typer, con decoradores repetitivos y sin
  inferencia de tipos desde anotaciones), `fire` (menos control de la ayuda
  y de la validación).

### Rich

- **Justificación:** salida legible en terminal mediante tablas
  (`Rich.Table`) para `listar`, `buscar` y `resumen`, y mensajes con estilos
  (`[yellow]`, `[simulación]`) en `contar` y avisos. Se integra de forma
  natural con Typer (ambos del mismo autor).
- **Alternativas descartadas:** `print` plano (salida pobre y sin
  alineación), `textual` (interfaz TUI completa, excesiva para una CLI),
  `tabulate` (solo tablas, sin consola ni estilos).

## 3. Configuración de acciones mediante `acciones.json`

- **Decisión:** toda acción nueva o modificada se lee de `acciones.json`
  (raíz del proyecto); nunca se codifica (hardcodea) en el código fuente.
  Esto lo exige `AGENTS.md` y lo aplica `src/cli_tareas/acciones.py`.
- **Contenido actual:** `listar`, `contar`, `buscar`, `resumen`, `describir`
  y `clasificar`, cada uno con `activa` (interruptor on/off), `descripcion`,
  `ruta_predeterminada` (`~/pruebas-tareas`) y parámetros específicos
  (`incluir_carpetas`, `ordenar_por`, `max_resultados`, `max_ficheros`).
- **Validación:** el módulo `acciones.py` define un esquema por acción
  (`ESQUEMAS: dict[str, dict[str, type]]`) y comprueba:
  - existencia de la acción y de su esquema (`AccionNoDefinidaError` o
    `ConfiguracionInvalidaError`),
  - que esté activa (`AccionDesactivadaError`),
  - rechazo de claves desconocidas,
  - tipos de cada clave, valores positivos y valores permitidos para
    `ordenar_por` (`ConfiguracionInvalidaError`, p. ej. `max_resultados` > 0
    y no booleano).
- **Predeterminados:** las claves opcionales ausentes se completan en
  `PREDETERMINADOS` (`listar`: `incluir_carpetas=true` y
  `ordenar_por=nombre`; `contar`: `incluir_carpetas=false`; `buscar`: sin
  límite; `describir` y `clasificar`: `max_ficheros=10`). Así el
  comportamiento no depende de valores ocultos en la capa CLI.
- **Justificación:** separar datos de lógica permite desactivar acciones,
  cambiar rutas y límites sin modificar código ni recompilar, y añadir
  acciones declarativamente. JSON es un formato que ya domina el alumnado
  de DAM y no requiere dependencias adicionales (módulo estándar `json`).
- **Alternativas descartadas:**
  - Constantes en Python: obliga a editar y probar código para cambiar
    parámetros; contradice `AGENTS.md`.
  - YAML/TOML: TOML requiere dependencia externa (o `tomllib`, válido en
    3.11+); YAML exige `pyyaml` y es más propenso a errores de formato.
  - Base de datos: sobredimensionado para un proyecto educativo.

## 4. Diseño del motor de acciones

La arquitectura separa tres capas, con módulos pequeños y funciones puras
cuando es posible (criterio de `AGENTS.md`):

```
┌─────────────────────────────────────────────────────┐
│ main.py  (capa de presentación y orquestación)      │
│  Comandos Typer: version, listar, contar, buscar,   │
│  resumen, describir, clasificar. Renderiza Rich.    │
└──────────────┬──────────────────────────────────────┘
               │ _iniciar(nombre, ruta, simular, msg)
               ▼
┌─────────────────────────────────────────────────────┐
│ acciones.py (motor de configuración)                │
│  cargar_acciones() → obtener_config() → validar()   │
└──────────────┬──────────────────────────────────────┘
               ▼
┌─────────────────────────────────────────────────────┐
│ ficheros.py (capa de dominio/E.S. del sistema)      │
│  resolver_ruta, validar_carpeta, obtener_entradas,  │
│  ordenar_entradas, formatear_*                      │
└─────────────────────────────────────────────────────┘
```

- **Flujo común de toda acción** (`main.py`, `_iniciar`):
  1. `cargar_acciones()` lee y valida el JSON raíz.
  2. `obtener_config()` obtiene, activa y valida la configuración.
  3. `resolver_ruta()` resuelve la carpeta (argumento del usuario o
     `ruta_predeterminada`, con `expanduser()` para `~`).
  4. Si `--simular`, muestra el mensaje previsto y termina sin efectos.
  5. En caso contrario, ejecuta la acción y renderiza el resultado.
- **Errores:** jerarquía propia en `excepciones.py` (`ErrorAccion` y
  derivadas) convertida en `typer.Exit(code=1)` en la capa de comandos.
  Los errores de preparación se agrupan en `ERRORES_PREPARACION`.
- **Presentación separada del dominio:** `listar.py`, `contar.py`,
  `buscar.py`, `resumen.py`, `describir.py` y `clasificar.py` solo
  construyen tablas/textos a partir de datos; las operaciones de ficheros
  viven en `ficheros.py` y la integración con IA en `ia.py`. Esto permite
  probar la lógica sin tocar el terminal.
- **Justificación:** el patrón «configurar → validar → resolver → actuar»
  hace que cada acción nueva sea casi declarativa; las funciones puras
  (`ordenar_entradas`, `construir_tabla`, `limitar_resultados`) son
  triviales de testear.
- **Alternativa descartada:** un único fichero monolítico con toda la
  lógica (más difícil de probar y de mantener, contrario a la modularidad
  exigida).

## 5. Modo `--simular` y medidas de seguridad

- **Decisión:** toda acción con efectos externos acepta `--simular`, que
  muestra el mensaje de lo que se haría («Se listaría…», «Se contarían…»)
  y termina con `typer.Exit()` sin ejecutar nada. Es un requisito de
  `AGENTS.md` verificado en las 6 acciones actuales (en `describir` y
  `clasificar` la simulación se corta antes de la capa de IA, sin red).
- **Otras medidas de seguridad:**
  - `activa: false` en `acciones.json` desactiva una acción de forma
    centralizada.
  - Validación estricta de tipos, rangos, claves desconocidas y valores
    permitidos de la configuración antes de actuar, con predeterminados
    declarados en `PREDETERMINADOS`.
  - `max_resultados` limita la salida de `buscar` con aviso de recorte.
  - Errores controlados (`PermissionError`, carpetas inexistentes) con
    mensajes claros y código de salida 1, sin trazas brutas.
  - No hay acciones de escritura/borrado: el alcance actual es de solo
    lectura del sistema de ficheros.
  - Reglas del proyecto (`AGENTS.md` y `opencode.json`): sin secretos en
    el repo, sin modo `--auto`, Git denegado por defecto para los agentes
    y limitado a consultas de solo lectura (`git status`, `git diff`,
    `git log`, `git show` y `git --version`), archivos de prueba solo en
    `~/pruebas-tareas`. La sintaxis y la precedencia se verificaron con
    OpenCode 1.18.35 (`opencode debug config` y `opencode agent list`).
  - La allowlist Git es defensa en profundidad, no aislamiento absoluto:
    rutas completas a `git.exe`, alias, envoltorios de PowerShell/CMD,
    pipes y otra configuración de Git pueden eludir los patrones de
    prefijo. Los commits manuales del usuario no se ven afectados.
- **Justificación:** en un proyecto asistido por IA es imprescindible
  poder prever el efecto de una operación antes de ejecutarla; la
  simulación actúa de red de seguridad tanto para el usuario como para el
  agente de desarrollo.
- **Alternativas descartadas:** confirmación interactiva por acción
  (rompe la automatización de pruebas y encadena preguntas), entorno
  aislado tipo sandbox (sobredimensionado para operaciones de lectura).

## 6. Alternativas globales consideradas y sus inconvenientes

| Alternativa | Inconvenientes |
|---|---|
| Shell script (PowerShell/Bash) | Sin tipado ni pruebas unitarias cómodas; portable solo a una plataforma. |
| Node.js/TypeScript | Requiere toolchain distinto al exigido; gestión de dependencias más frágil en el aula. |
| GUI (tkinter/PyQt) | Contradice el requisito de CLI; más coste de desarrollo y pruebas. |
| Acciones hardcodeadas en Python | Viola el requisito de configuración externa; cualquier cambio exige editar código. |
| Sin modo simulación | Impide prever efectos; riesgo en un contexto asistido por IA. |

## 7. Consecuencias

### Positivas

- Interfaz de terminal profesional con ayuda autogenerada y salida
  formateada.
- Cambios de comportamiento (rutas, límites, ordenación) sin tocar código.
- Arquitectura modular con funciones puras: 189 pruebas automatizadas
  superadas y lint limpio con ruff.
- Seguridad verificable: simulación, interruptores de acciones y
  validación de configuración.
- Base preparada para acciones futuras de IA siguiendo el mismo motor.

### Negativas

- Mantener `ESQUEMAS` en `acciones.py` duplica parcialmente la estructura
  de `acciones.json`; añadir una acción requiere tocar ambos.
- JSON no admite comentarios, lo que limita la autodocumentación del
  fichero de configuración.
- La validación de esquemas es artesanal; si crece, convendrá migrar a
  `pydantic` (ya presente como dependencia transitiva).
- El punto de `ruta_predeterminada` apunta a `~/pruebas-tareas`, fuera del
  repo: requiere que esa carpeta exista en cada máquina.
